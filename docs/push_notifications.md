# Механизм отправки push-уведомлений

**Актуализация:** 2026-08-13

## Общая схема

Уведомления не отправляются в момент события: они складываются в таблицу и рассылаются
периодической задачей — так же, как письма в `django-post_office`, на котором основан пакет.

```
событие (FSM-переход сущности)
  -> edw.models.notification.Notification.notify_by_push
  -> fcm_async.push.send            создаёт PushNotification со статусом queued
  -> celery beat: send_queued_notifications (раз в минуту)
  -> fcm_async.push.send_queued -> _send_bulk
  -> PushNotification.deliver -> send_firebase -> FCM v1 API
```

Одна запись `PushNotification` — это одно уведомление одному получателю. В поле `to` лежат
все токены устройств этого получателя, разделённые переводом строки.

## Формат сообщения

Сообщение собирается в [`PushNotification.send_firebase`](../fcm_async/models.py). Кто
показывает уведомление — операционная система или мобильное приложение — определяет
настройка `FCM_ASYNC['SEND_SYSTEM_NOTIFICATION']`, от неё же зависит, как передаётся ссылка.

### Системное уведомление, `SEND_SYSTEM_NOTIFICATION = True`

| Блок | Зачем |
|------|-------|
| `notification` | Уведомление показывает сама ОС, даже когда приложение выгружено |
| `apns` | `apns-push-type: alert`, `apns-priority: 10`, `aps.alert` — видимое уведомление на iOS |
| `android` | `priority: high`, `notification` — доставка вне зависимости от Doze, показ силами Android |
| `data` | Обработчик мобильного приложения: ключи `title`, `body` и `url` |

Текст показывает ОС, поэтому разметка из него вырезается, а адрес первой ссылки уезжает
отдельным ключом `data.url` — по нему приложение открывает нужный экран. Адрес берёт
`extract_url` до вырезания тегов; ради этого `render_and_clean` и оставляет теги `<a>`
нетронутыми. Если ссылок в шаблоне нет, ключа `url` в `data` не будет и нажатие просто
откроет приложение.

Кто именно показывает уведомление на Android, зависит от состояния приложения: свёрнутому
приложению уведомление показывает система по блоку `notification`, а открытому на экране FCM
SDK ничего не показывает и передаёт сообщение в обработчик, который рисует уведомление из
`data`. Поэтому в этом режиме возможно дублирование — системное уведомление плюс собственное;
обработчик приложения должен показывать своё уведомление только когда системное не
отображается. По той же причине в `aps` не выставляется `content_available`: вместе с видимым
`alert` он будит обработчик приложения в фоне, и тот рисует второе уведомление поверх
системного.

### Уведомление рисует приложение, `SEND_SYSTEM_NOTIFICATION = False`

| Блок | Зачем |
|------|-------|
| `notification` | Не передаётся |
| `apns` | `apns-push-type: background`, `apns-priority: 5`, `aps.content-available` — фоновая доставка |
| `android` | `priority: high` без `notification` — доставка вне зависимости от Doze |
| `data` | Обработчик мобильного приложения: ключи `title` и `body` |

Ссылки в этом режиме из текста не вырезаются и передаются в `data.body` как есть, вместе с
тегами `<a href="...">`: уведомление рисует приложение, оно же разбирает разметку. Ключ
`data.url` не передаётся.

Режим повторяет поведение пакета до августа 2026 года, за исключением приоритета Android
(был `normal`). Такое сообщение не показывается операционной системой, а iOS дополнительно
жёстко ограничивает количество фоновых доставок (единицы в час на устройство) и не доставляет
их вообще, если приложение выгружено пользователем. При отправке нескольких уведомлений
подряд большая часть теряется — именно из-за этого и появился режим системного уведомления.

### Ограничение размера

Шаблоны уведомлений общие с email, поэтому текст приходит с разметкой и может быть очень
длинным, а лимит сообщения FCM и APNs — 4096 байт. `PushNotification.get_payload`:

1. ставит перенос строки на место `<br>`, `</p>`, `</li>` и прочих тегов, разделяющих строки
   и абзацы (`break_lines`) — вырезанные без замены, они склеивают соседние строки в одно слово;
2. вырезает HTML-сущности и, если уведомление показывает ОС, теги (`strip_tags`, `html.unescape`);
3. сворачивает пробелы внутри строк и убирает пустые строки, сохраняя переносы
   (`normalize_whitespace`); заголовок при этом сводится к одной строке;
4. обрезает заголовок и текст по `MAX_TITLE_LENGTH` и `MAX_BODY_LENGTH`;
5. подгоняет результат под байтовый бюджет. С системным уведомлением заголовок и текст
   попадают в payload дважды (`notification`/`alert` и `data`), поэтому бюджет делится на две
   копии, без него — остаётся целиком под одну.

Адрес перехода не обрезается, иначе ссылка перестанет открываться, — его размер вычитается
из бюджета до деления между копиями заголовка и текста. Если обрезка текста со ссылками
разорвала тег, его хвост убирается, чтобы не ломать разбор разметки в приложении.

## Обработка ответа FCM

`messaging.send_each_for_multicast` не поднимает исключение при ошибке отдельного токена —
он возвращает `BatchResponse` с результатом по каждому токену. Разбор ответа выполняет
`PushNotification.process_batch_response`, результат возвращается в виде `DeliveryResult`:

| Поле | Значение |
|------|----------|
| `status` | `sent`, если принят хотя бы один токен, иначе `failed` |
| `message` | Ошибки по токенам с маскированными токенами, попадает в `Log` |
| `exception_type` | Типы ошибок FCM |
| `transient` | Есть ли смысл повторить отправку |
| `invalid_tokens` | Токены, которых больше не существует |
| `success_count` / `failure_count` | Счётчики по токенам |

### Статусы записи

| Ситуация | Статус | Поведение |
|----------|--------|-----------|
| Принят хотя бы один токен | `sent` | Ошибки остальных токенов пишутся в `Log` |
| Временная ошибка, попытки не исчерпаны | `queued` | `number_of_retries + 1`, `scheduled_time = now + RETRY_INTERVAL` |
| Временная ошибка, попытки исчерпаны | `failed` | Больше не отправляется |
| Постоянная ошибка | `failed` | Больше не отправляется |

Временными считаются ошибки FCM с кодами `UNAVAILABLE`, `INTERNAL`, `DEADLINE_EXCEEDED`,
`RESOURCE_EXHAUSTED` (в том числе `QuotaExceededError`), `ABORTED`, `UNKNOWN`, а также
сетевые сбои. Постоянными — ошибки подготовки сообщения (`ValueError`, `TypeError`,
`KeyError`, `AttributeError`) и остальные ошибки FCM, включая `InvalidArgumentError`.

### Удаление недействительных токенов

Токены, отвергнутые с `UnregisteredError` или `SenderIdMismatchError`, передаются
обработчику из настройки `FCM_ASYNC['INVALID_TOKEN_HANDLER']` — пакет не знает о моделях
проекта. В `nash_region` обработчик удаляет токены из JSON-поля
`BasePerson.firebase_tokens` (`BasePerson.remove_firebase_tokens`). Без этого мёртвые
токены остаются у получателя навсегда, и каждое уведомление уходит в том числе на них.

`InvalidArgumentError` («registration token is not a valid FCM registration token») токен
не удаляет: этой же ошибкой FCM отвечает на некорректный payload, и удалять токены из-за
ошибки в формате сообщения нельзя.

## Параллельность отправки

`_send_bulk` рассылает пачку в `THREADS_PER_PROCESS` потоков, при этом сама
`send_each_for_multicast` внутри `firebase_admin` дополнительно распараллеливается по
токенам получателя. Все потоки работают через одну HTTP-сессию, поэтому:

- перед запуском потоков вызывается `warmup_credentials()` — иначе каждый поток обнаруживает
  просроченный токен доступа и запускает свой refresh, а `firebase_admin` не перехватывает
  `RefreshError` внутри отправки и роняет всю пачку сообщений целиком;
- значение `THREADS_PER_PROCESS` держим небольшим, увеличивать его без необходимости не стоит.

Уведомления, для которых не удалось отрендерить шаблон, до потоков не доходят: они сразу
помечаются как неудачные.
