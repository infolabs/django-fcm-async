# Диагностика недоставки уведомлений

**Актуализация:** 2026-08-13

## Порядок проверки

### 1. Пакет вообще включён

```python
from django.conf import settings
from fcm_async.models import FIREBASE_APP
import edw.models.notification as n

settings.FIREBASE_KEY_PATH  # путь до сервисного ключа
FIREBASE_APP                # None означает, что отправка отключена
n.push                      # None означает, что edw не увидел FIREBASE_KEY_PATH на импорте
```

`edw.models.notification` импортирует `fcm_async` только если `FIREBASE_KEY_PATH` уже
установлен, поэтому важен порядок инициализации приложений.

### 2. Уведомления создаются

```python
from fcm_async.models import PushNotification
PushNotification.objects.order_by('-id').values('id', 'created', 'status')[:20]
```

Если записей нет, проблема выше по потоку: не настроено `Notification` для перехода,
у получателей нет токенов либо стоит `do_not_receive_notifications`.

### 3. Очередь разбирается

Записи со статусом `queued` и `scheduled_time` в прошлом должны исчезать в течение минуты.
Если очередь растёт, проверьте задачу `send_queued_notifications` в django-celery-beat, лог
celery и файл блокировки `/tmp/fcm_async.lock`.

### 4. Что ответил FCM

```python
from fcm_async.models import Log
Log.objects.order_by('-id').values('date', 'notification_id', 'status', 'exception_type', 'message')[:20]
```

Статус `sent` с непустым `message` означает частичную доставку: часть токенов получателя
отвергнута. Полезные типы ошибок:

| Тип | Значение |
|-----|----------|
| `UnregisteredError` | Приложение удалено или токен протух, токен будет удалён у получателя |
| `SenderIdMismatchError` | Токен выпущен другим проектом Firebase, токен будет удалён |
| `InvalidArgumentError` | Некорректный токен или payload, повторов не будет |
| `QuotaExceededError` | Превышены лимиты FCM, будет повтор |
| `UnavailableError`, `InternalError` | Временная недоступность FCM, будет повтор |
| `ThirdPartyAuthError` | Проблема с сертификатом APNs в консоли Firebase |

### 5. Проверка доставки на конкретное устройство

```bash
python manage.py send_test_push --dry-run <token>   # проверить формат сообщения и токен
python manage.py send_test_push <token>             # доставить уведомление на устройство
python manage.py send_test_push --data-only <token> # то же без системного уведомления
```

## Уведомление показывается дважды

Системное уведомление показывает ОС, а те же `title` и `body` уходят в `data`, поэтому
обработчик мобильного приложения может нарисовать поверх ещё одно. Правильное решение — на
стороне приложения: показывать своё уведомление только когда системное не отображается.
Пока приложение не доработано, дублирование убирает `FCM_ASYNC['SEND_SYSTEM_NOTIFICATION']
= False`, но тогда возвращаются потери доставки, ради которых системное уведомление и
добавлялось, см. [push_notifications.md](push_notifications.md#формат-сообщения).

## FCM принял сообщение, но на Android ничего не появилось

Сначала посмотрите, в каком состоянии было приложение: от этого зависит, кто показывает
уведомление.

| Состояние приложения | Кто показывает |
|----------------------|----------------|
| Свёрнуто или закрыто | Система, по блоку `notification` |
| Открыто на экране | Приложение, из `data`; системный показ не выполняется вовсе |
| Выгружено свайпом из списка задач | Никто, FCM не доставляет ничего до следующего запуска |

Проверять доставку при открытом приложении бессмысленно: FCM SDK в этом состоянии не
показывает `notification` сам, а вызывает обработчик приложения, и результат целиком зависит
от него. Сворачивайте приложение кнопкой «Домой» и ждите несколько секунд.

Второе — `FCM_ASYNC['ANDROID_CHANNEL_ID']`. Уведомление, адресованное каналу, которого
приложение не создавало, Android отбрасывает молча: FCM возвращает `message_id`, в логах
пакета всё успешно, а на устройстве не появляется ничего (в logcat — «No Channel found for
pkg=...»). Пустое значение настройки безопасно: сообщение уйдёт в канал по умолчанию.

Дальше — разрешение на уведомления у приложения (с Android 13 его спрашивают явно),
не выключен ли канал в системных настройках уведомлений и экономия батареи на прошивках
вендоров.

## Уведомление приходит, но без звука на Android

Начиная с Android 8 звук, вибрация и всплытие задаются каналом уведомлений, а не сообщением:
поля `sound` и `default_sound` на этих версиях игнорируются. Уведомление попадает в канал,
указанный в `FCM_ASYNC['ANDROID_CHANNEL_ID']`, либо в канал по умолчанию из манифеста
приложения, либо в резервный канал FCM SDK — и звучит так, как настроен этот канал.

Если приложение открыто на экране, уведомление рисует оно само в своём канале, и параметры
сообщения на звук не влияют совсем. В `nash_region` беззвучным оказался именно этот случай:
системные уведомления звучат в резервном канале FCM, а нарисованное приложением — молчит.
Лечится только на стороне приложения.

Порядок действий, если молчит и системное уведомление: узнать у мобильной команды
идентификатор канала со звуком и прописать его в `ANDROID_CHANNEL_ID`. Идентификатор нужно
именно узнать, а не предположить: с выдуманным значением уведомление перестанет показываться
вовсе. Альтернатива на стороне приложения — объявить в манифесте
`com.google.firebase.messaging.default_notification_channel_id` с каналом важности
`IMPORTANCE_HIGH`. Канал с сервера создать нельзя.

Учтите, что пользователь мог сам отключить звук для канала в системных настройках, а
изменение параметров уже созданного канала из кода приложения не применяется — приложению
нужно создавать новый канал с другим идентификатором.

## Известные внешние ограничения

Даже принятое FCM сообщение может не дойти до устройства:

- **iOS**: приложение не имеет разрешения на уведомления; в консоли Firebase не загружен
  ключ APNs; уведомление отправлено как `background` — такие пуши Apple троттлит и не
  доставляет при выгруженном приложении.
- **Android**: сообщение без блока `notification` и с приоритетом `normal` откладывается в
  Doze и не показывается системой; агрессивная экономия батареи на прошивках вендоров
  блокирует доставку выгруженному приложению.
- **Оба**: истёк `TTL` (по умолчанию час), пока устройство было офлайн. Для несклеиваемых
  сообщений FCM хранит не более 100 штук на устройство и при переполнении отбрасывает всю
  накопленную очередь.

Формат сообщения, который отправляет пакет, описан в
[push_notifications.md](push_notifications.md).
