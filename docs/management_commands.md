# Команды управления

**Актуализация:** 2026-08-13

## send_queued_notifications

Рассылает уведомления из очереди: статус `queued` и `scheduled_time` в прошлом или пустой.

```bash
python manage.py send_queued_notifications [-p N] [-L /path/to/lockfile] [-l 0|1|2]
```

| Аргумент | Назначение |
|----------|------------|
| `-p`, `--processes` | Количество процессов, по умолчанию `1` |
| `-L`, `--lockfile` | Путь до файла блокировки, по умолчанию `/tmp/fcm_async` |
| `-l`, `--log-level` | Переопределяет `FCM_ASYNC['LOG_LEVEL']` |

Команда берёт файловую блокировку, поэтому параллельные запуски завершаются сразу. Внутри
цикл повторяет проходы по `BATCH_SIZE` уведомлений, пока очередь не опустеет.

Значение `-p` больше `1` использовать не рекомендуется: рассылка идёт через
`multiprocessing.Pool`, а дочерние процессы наследуют открытые соединения с FCM, что
приводит к сетевым сбоям. Параллельность внутри процесса задаётся `THREADS_PER_PROCESS`.

В `nash_region` команда вызывается celery-задачей `send_queued_notifications`
(`nash_region/celery.py`), запланированной в django-celery-beat раз в минуту.

## send_test_push

Отправляет тестовое уведомление на указанные токены и печатает ответ FCM по каждому токену.
Нужна для проверки доставки без ожидания периодической задачи; запись в базу не создаётся.

```bash
python manage.py send_test_push <token> [<token> ...] [-t Заголовок] [-m Текст] [--dry-run]
                                [--system | --data-only]
```

| Аргумент | Назначение |
|----------|------------|
| `tokens` | Один или несколько токенов устройств |
| `-t`, `--title` | Заголовок уведомления |
| `-m`, `--text` | Текст уведомления, ссылку можно задать тегом `<a href="...">` |
| `-d`, `--dry-run` | Проверить сообщение на стороне FCM без доставки на устройства |
| `-s`, `--system` | Отправить с системным уведомлением |
| `-D`, `--data-only` | Отправить только data-сообщение |

Команда печатает итоговый заголовок и текст после обрезки, размер payload, а по каждому
токену — `message_id` либо ошибку с пометкой, будет ли токен удалён и будет ли повтор.

`--system` и `--data-only` переопределяют настройку `FCM_ASYNC['SEND_SYSTEM_NOTIFICATION']`
на одну отправку — так можно сравнить оба варианта на живом устройстве, не меняя настройки.

Пример проверки формата сообщения без доставки:

```
$ python manage.py send_test_push --dry-run fake-token
Проект: narod-expert
Заголовок: Тестовое уведомление
Текст: Проверка доставки push-уведомлений
Размер заголовка и текста: 100 байт
Режим проверки, уведомления на устройства не доставляются
fake-token: The registration token is not a valid FCM registration token (InvalidArgumentError)
Принято 0 из 1 токенов
```

## cleanup_notifications

Удаляет уведомления вместе с их логами, созданные раньше чем указанное количество дней назад.

```bash
python manage.py cleanup_notifications [-d N]
```

| Аргумент | Назначение |
|----------|------------|
| `-d`, `--days` | Возраст удаляемых уведомлений в днях, по умолчанию `90` |

Аналогичная celery-задача `cleanup_push_notifications` описана в
[`fcm_async/tasks.py`](../fcm_async/tasks.py), по умолчанию хранит уведомления 90 дней.
